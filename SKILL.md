# CASFRI inventory ingestion

Use [the detailed inventory procedure](documentation/new_inventory_ingestion_procedure.md) as the authoritative procedure. Read its relevant sections before working; resolve script behavior against the current repository rather than relying on an archived document. Paths in this skill are relative to the CASFRI project root. User instructions take precedence over this skill.

1) **Establish the task and scope** - Distinguish documenting the procedure from actually processing an inventory. Documentation edits do not authorize running database operations. For a new inventory, establish its source files, jurisdiction, identifier, standard, and intended database from available project information. Ask for missing information only when it blocks the requested work. NB99 is a fictitious example; do not treat it as a real inventory.

   Keep the three database tasks distinct: translating a new inventory follows the detailed guide; building the whole database follows [the main README](README.md#build-the-whole-database-from-scratch); producing a release follows [the release procedure](documentation/release_procedure.md). Adding an inventory does not imply rebuilding the database or publishing a release.

2) **Follow the detailed procedure** - Use its current section titles, commands, configuration variables, and checks. Follow the file table's "Change required" column: optional edits become required when their stated condition applies, and generated files should be regenerated using the designated scripts. The six stages are:

   - Archive and document the inventory. Record inventory metadata in [inventory_metadata.csv](metadata/inventory_metadata.csv), using dedicated columns and `COMMENT` for additional explanations. Follow subsection 1.2 of the detailed procedure for lengthy comments and inventory README references. Explain the full rule only there; elsewhere, documentation instructions should refer to the `COMMENT` column "or the inventory's README". Keep the summary and README reference in `COMMENT`. Retain original deliveries and manuals in the source archive.
   - Prepare the environment, convert and load the inventory. A configured local `config.sh` is required: if absent, copy `config_sample.sh` to that name and configure it before processing. An existing configuration file needs editing only when its configuration variables must change. Start from a comparable conversion script and inspect polygon shapes before accepting metadata counts. Prefer `./convert_all.sh` with `postProcessing=True` for automatic count checks; running an inventory conversion script directly requires a separate manual count check. Add new photograph-year shapefiles to `photoYearList`. Keep the explanation of this variable and its loading behavior in the main README.
   - Prepare and validate the translation. Configure input-layer mappings and dependencies, load the translation tables and metadata, and inspect sample translations before processing the complete inventory. Treat `TRANSLATION_ERROR` (`-3333`) as a translation-code bug to correct before accepting results; rerun the affected translation and tests. Review sample error codes against the inventory manual: valid new source values may require adapting translation tables or CASFRI helper functions. Keep the brief row-filtering explanation in the main README. After the field table in subsection 3.2 of the detailed procedure, discuss fields in their table order, refer general translation-table writing instructions to the framework guide, and retain CASFRI-specific requirements and examples together with the requested explanation of `ROW_TRANSLATION_RULE` filtering. Link to the PostgreSQL Table Translation Framework in both documents. Follow [section 3.1 of the detailed procedure](documentation/new_inventory_ingestion_procedure.md#31-add-mapping-rows-in-layer_metadatacsv) for quoting and fixed values, including `NULL`.
   - Translate the complete inventory. Run `TT_DropAllConstraints(schemaName, tableName)` for each of CAS, DST, ECO, LYR, NFL, and GEO first. Refresh only the inventory's HDR row using the delete-and-insert transaction in subsection 4.2, then translate all six tables in parallel with `./02_translateAll.sh`. Wait for every process to finish and check translated row counts using either method in subsection 4.4, then run `workflow/02_produceCASFRI/03_ConstraintsChecksAndIndexes/01_addConstraints.sql`, followed by `01_addGeoConstraints.sql` from the same folder, to reapply and test the standard constraints. Resolve every failed check. Every constraint check that fails and remains unresolved must have a GitHub issue. The drop function uses `CASCADE`; restore any additional dependent constraints separately. Preserve existing inventories; do not run full-build initialization against results that must be retained. Check partial results before retrying to avoid duplicate rows.
   - Generate, validate and archive test tables. Use the complete translation validated in subsection 4.4 as the reference; repeat its count check only if translated data or expected counts have changed. Use the existing test-count checks, run tests of new or modified helper functions, and compare the generated test tables with accepted results. Test generation alone does not establish correctness. Sample tests exclude HDR and GEO; follow their separate checks and compare translated GEO coverage visually with the source polygons. Follow the guide's jurisdiction-wide test scope and preserve results for existing inventories.
   - Record and share the work. Complete metadata documentation and review the changed files. Guide readers to create GitHub issues for problems the procedure could not resolve and link them from the inventory documentation. When explaining how to share changes, present GitKraken, VS Code, and Git Bash as three alternative methods, chosen according to how the reader manages the repository (subsection 6.3). Commit, push, or update derived products only when included in the user's requested work.

3) **Prefer reuse when developing translations** - Reuse existing translation tables as much as possible, making simple modifications when they allow reuse. Create new tables when substantial changes are required or no suitable existing set is available. Before changing shared components, confirm existing affected inventories' test results match the archived files; rerun and compare after the changes, following the [translation-test README's development cycle](translation/test/readme.md#testing-procedure). Recheck every affected inventory, including other jurisdictions when shared components are used there.

   Use basic helper functions from the PostgreSQL Table Translation Framework wherever possible before writing specialized CASFRI functions. If those functions cannot meet the need, check existing CASFRI functions for reuse or adaptation. Whenever adding or modifying a function in [helperFunctionsCASFRI.sql](helperfunctions/helperFunctionsCASFRI.sql), add or update and run its tests in [helperFunctionsCASFRITest.sql](helperfunctions/helperFunctionsCASFRITest.sql). Add the corresponding removal command to [helperFunctionsCasfriUninstall.sql](helperfunctions/helperFunctionsCasfriUninstall.sql) for a new function. Consult the framework's local `helperFunctions.sql` file and documentation when selecting its basic validation and translation functions; the detailed guide's file table links to this file in the separate framework repository.

4) **Maintain the documents and this skill together** - Whenever the detailed guide changes, review this skill in the same task. Update any affected instructions, terminology, references, or workflow decisions. Pure formatting changes need no redundant rewrite here. Keep detailed commands and column descriptions in the guide rather than copying them into this skill.

   Refer to the [Shared preparation](README.md#shared-preparation) section from the main README using that exact linked wording.

   Edit the detailed guide by default. Update the main README when the user requests it; keep corresponding procedure titles and wording aligned when changing both. Preserve the user's concurrent edits by reading files immediately before making changes.

   Keep the detailed procedure as brief as possible without omitting important steps or repeating instructions. Maintain a consistent heading hierarchy, with numbered subsections such as 1.1 and 1.2. Keep the six main steps numbered and titled consistently in both documents. In the main README, add a link labeled "(detailed)" at the end of each of the six inventory procedure section titles, pointing to its corresponding detailed section. Keep the section numbers unlinked and do not add these links to the detailed procedure headings.

   Write for a nonprogrammer. When referring to a function by name, append empty parentheses, for example `TT_Prepare()`. Preserve arguments in actual calls and function signatures. Write column names in uppercase in documentation prose and tables. When referring to a column in prose, prefer "the `COLUMN_NAME` column" where natural; use plural wording for lists, and distinguish column names from their values. Identify the table or file containing a column when its location would otherwise be ambiguous. When specifying a value to enter, write "set `COLUMN_NAME` to `value`", for example "set `LAYER_RANK` to `1`". Always prefer "set" over "use" for column-value assignments. Preserve the exact case of cell values, including source-column names and placeholders stored in layer_metadata.csv, and preserve actual spelling in executable examples and CSV headers. State the capitalization convention once near the beginning of each document, with an exception for values whose required spelling uses capitals; do not repeat this editorial convention in procedure subsections. Use numbered steps and subsections, with a bold title followed by ` - ` and a capitalized explanation. Reserve "conversion" for source-format conversion and loading; use "translation" for applying CASFRI rules, and "lookup tables" for code correspondences. Say "translated table" rather than "result table" for translated data. Write "value checks" without a hyphen. Name the specific constraint, comparison, or expected outcome instead of using vague validation wording. Use "CASFRI tables" for translated output tables, "translation tables" for tables containing rules, "configuration variables" for configuration values, and "denormalized (flat) table" for flat outputs. Explain how to open Git Bash where needed and prefix executable `.sh` paths with `./`, preserving necessary `../` paths.

   Number review findings and include a direct link to each location, the quoted text, and a proposed replacement. When presenting changes for the user to select or approve, use clickable choices through the available user-input tool rather than Markdown checkboxes; apply only the selected items.

   After editing the main README or detailed procedure, open VS Code comparisons against their versions before the edits. Show comparisons only for those documents; do not open skill-file comparisons.
